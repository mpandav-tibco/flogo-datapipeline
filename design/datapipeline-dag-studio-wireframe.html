A DAG-native pipeline studio — inside VS Code

The Data Pipeline Studio is a VS Code extension: authors design entirely in the editor, in a webview canvas that themes to VS Code. This revamp keeps the shell and persona of the TIBCO Flogo 3.x designer already in this workspace — an activity-bar container, a project sidebar, and a custom flow editor — and upgrades the canvas from a linear source→transforms→sink chain to a first-class directed-acyclic graph: multiple sources, multiple sinks, branch & merge, typed ports, wire-to-connect, schema-on-the-edge, and a live run overlay.

Vision & design principles

Job to be done: a data engineer should be able to see and shape the whole topology — where data comes from, how it branches, where every row ends up — without opening a single JSON blob or config panel to understand the shape.

1 · The graph is the source of truth

Nodes are stages; edges are dataflow. Everything a row can do — split, join, be rejected — is a visible wire, not a hidden field. What you see is what runs.

2 · Typed ports, safe wires

Each node exposes named input/output ports (a join has left+right; a router has one port per route; any stage can expose an error port). Wires only connect compatible ports; cycles are refused.

3 · Schema propagates down the edge

Hover or select an edge to see the column schema crossing it. Downstream nodes inherit it, so mappers/validators offer real column names — NiFi-style provenance meets Talend-style schema propagation.

4 · Author by direct manipulation

Drag a component from the palette; drag from an output port to an input port to wire it; drop a wire on empty canvas to quick-add the likely next node. No modal wizards.

5 · The run lives on the graph

During a run, every node shows in-flight counts, throughput and status; every edge animates. Back-pressure and the reconciled funnel (read → transformed → written / rejected / dropped) are read straight off the topology.

6 · Progressive disclosure — auto-layout by default

Auto-layout is on by default: a linear pipeline stays a tidy left→right line and nodes place themselves, so no one pays the "arrange the boxes" tax. Manual positioning is opt-in for when you want it. Complexity — sub-pipelines, groups, many branches — is available but never forced; a minimap + zoom keep big graphs navigable.

Palette & authoring interactions

Everything is direct manipulation — the muscle memory of NiFi / Node-RED / n8n, with the guardrails of a typed graph.

Adding & connecting

  • Drag a palette component onto the canvas → a node with its ports appears.
  • Drag from an output port to an input port → a wire. Incompatible ports are dimmed while dragging.
  • Drop a wire on empty canvas → a context menu of the most likely next nodes (source→transform, transform→sink), pre-wired.
  • ＋ on an edge → insert a transform in-line (splices the wire).
  • Right-click node → duplicate, delete, add error port, wrap in group, "extract as sub-pipeline".
  • Multi-select (marquee / ⌘-click) → move, align, copy/paste, group.

Infer, don't hand-type

Nested & arrays

flatten turns nested objects into dotted columns; explode expands an array column into one row per element; parse pulls columns from text/JSON via regex named groups.

Any output format

Groups, sub-pipelines & reuse

Big graphs stay legible and DRY through three distinct mechanisms — a group (visual collapse), a reusable sub-pipeline (a saved, parameterised fragment), and coupled pipelines (independent pipelines chained through durable tables). Pick the right one for the coupling you want.

Terminology — it is a “sub-pipeline”, never a “sub-flow”. In Flogo an app holds resources, and a flogo:flow and a flogo:datapipeline are peer resource types. Calling a reusable pipeline fragment a “sub-flow” would collide with the Flogo flow engine's own #subflow (a different action). A pipeline that reuses another pipeline is a sub-pipeline.

Three ways to compose — and the coupling each gives you

Group UI · now

A visual boundary over a sub-DAG. Declutter a big graph; zero runtime effect. Ships with the renderer — no engine change.

Sub-pipeline new

A parameterised fragment referenced by name and inlined at compile. DRY logic across feeds — address-clean, PII-mask, SCD2. Net-new: a pipeline-ref node + inliner.

Coupled pipelines works today

Split a big job into independent pipelines chained through durable JDBC tables (queues). Each scales / checkpoints / monitors alone — example 19's pattern.

Lanes & sticky notes UI

Background lanes (ingest · quality · route · load) and sticky notes document intent without changing the run — swimlanes, à la Talend. Pure annotation, saved in the side-car ui block so the graph JSON stays clean.

Versioning & governance

A sub-pipeline carries a version (like the pipeline's own version field); bumping it flags dependents. Fragments live in the workspace or a shared library repo, so teams reuse vetted logic instead of copy-paste.

Scope honesty: groups and lanes are UI-only (ship with the canvas); coupled pipelines via shared tables already work (example 19). The one net-new engine piece is the sub-pipeline node — a pipeline-ref stage that inlines a saved fragment into the graph at compile — alongside the graph runner + union already noted.

Runtime graph model — how the DAG runs

The canvas needs a graph the engine can execute. Today Definition is source → transforms[] → sink. The revamp adds an optional graph form: nodes[] + edges[], compiled to the existing stage runners.

Proposed graph shape

{ "graph": { "nodes": [ { "id":"src_orders", "kind":"source", "type":"csv", ... }, { "id":"src_cust", "kind":"source", "type":"jdbc", ... }, { "id":"join1", "kind":"transform", "type":"join", "ports": { "in":["left","right"], "out":["rows"] } }, { "id":"val1", "kind":"transform", "type":"validate", "ports": { "out":["pass","reject"] } }, { "id":"route1","kind":"transform", "type":"router", "ports": { "out":["eu","us","rest"] } }, { "id":"snk_eu","kind":"sink","type":"s3-sink", ... }, { "id":"dlq1", "kind":"sink","type":"jdbc", ... } ], "edges": [ ["src_orders:rows","join1:left"], ["src_cust:rows", "join1:right"], ["join1:rows", "val1:in"], ["val1:pass", "route1:in"], ["val1:reject", "dlq1:in"], ["route1:eu","snk_eu:in"], ... ] } }

Compilation & guarantees

  • Topological compile — the engine sorts nodes by edges and runs them; a cycle is a load-time error (mirrors the editor's guard).
  • Fan-out (router / validate-reject) already exists as the router transform + a stage errorSink; edges just name the port that feeds each downstream.
  • Fan-in (join / union) already exists as the join transform (2 inputs) plus a new lightweight union (N inputs, same schema).
  • Back-compat — a file with source/transforms/sink and no graph runs exactly as today; the editor renders it as a linear graph and can "promote to graph" on first branch.
  • Single source of truth — Studio and CLI read the same file; positions live in a side-car ui block (as today) so the graph JSON stays clean.
Scope honesty: the UX revamp (this wireframe) is front-loaded, but a fully arbitrary DAG needs the engine's graph runner + a union stage. Everything else (join, router, validate error-port, introspect, metrics) already exists — the wireframe is grounded in shipped functionality.

Migration & phased rollout

Ship value continuously; never break the 26 existing example pipelines or the current linear authors.

Phase 1 — Visible branches

Render today's implicit branches on the existing canvas: draw the router's route-sinks and the join's reference source as real nodes + edges (read-only wires). No engine change. Immediate "I can see my DAG".

Phase 2 — Wire authoring

Free-canvas nodes, ports, drag-to-connect, edge insert, validation, minimap/zoom. Writes the graph block; still compiles branches through join/router/errorSink. Add the union stage.

Phase 3 — Graph runner & run overlay

Engine executes graph topologically; live per-node/edge counts, provenance sampling, groups/sub-pipelines. Deprecate nothing — linear files keep working.

Accessibility — designed in, proven early

  • Keyboard wiring — focus a node → P cycles its ports → Enter starts a wire → Tab to the target node/port → Enter connects. No mouse required.
  • Command-first — every canvas action (add, connect, delete, group) has a command-palette equivalent, so the graph is fully operable without pointer gestures.
  • Never colour-only — each state cue pairs colour with an icon + text label; status is announced, not just shown.
  • Screen-reader outline — the graph exposes a linear reading order: "orders.csv → join → validate → route(EU/US/rest) → …".
De-risk: node-graph a11y is genuinely hard — this is a commitment with a method, validated by a keyboard-only + screen-reader POC before we promise it in GA.
