00

Why VS Code changes the UX

The jobs, personas & principles are unchanged — but the IDE gives us native surfaces we should lean into, not fight. Validation becomes the Problems panel, quality becomes the Testing view, runs stream to the Output panel, and multi-pipeline dashboards become webview editors. The developer (Priya) is now the center of gravity; the operator (Marco) still gets a fleet — as a webview tab or CLI. This edition is aligned to the real flogo-3x extension baseline: it slots into the existing Flogo activity-bar container and reuses its custom-editor, mapper, diagram, execution-history & unit-test frameworks (see board 07).

Surface remap · web control-plane → VS Code

Pipeline builder canvas→Custom editor for .datapipeline
Run funnel & observability→“Run Report” webview + Output panel

Principles retained — expressed natively

1
Glass-box. Sample rows stream to the Data Preview panel; per-stage before/after with inline decorations in the editor.
2
Design ↔ run parity. The custom editor is also the monitor — nodes animate throughput; the same file, running.
3
Reconciled funnel. The Run Report webview + a Status Bar progress item; segments deep-link to Problems / DLQ.
4
Progressive disclosure. Inspector is a secondary side panel; advanced ops (scale, checkpoint) are collapsed until used.
5
Guardrails. Validate → squiggles + Problems; DQ → Testing pass/fail; DLQ captures rejects. Native, familiar, trusted.
6
Fleet scale. Trees handle 100s of pipelines; the “Fleet” webview gives the operator the dashboard when they want it.
Net new advantage of the IDE: Source Control — pipelines are files, so diff, blame, PR review & history come for free. No custom versioning UI needed.
i
Design rule for this edition: never rebuild what VS Code already does well. Reuse Problems, Testing, Output, SCM, Settings, Secret Storage, Walkthroughs.
ii
Reach parity by composition: only the canvas & dashboards are webviews; everything else is native contributions (fast, themable, accessible).

Validation → Problems panel, the single biggest IDE win — and flogo-3x already ships the helper: reuse buildDiagnostis() → a DiagnosticCollection with severity, source (flogo-dp), click-to-line + squiggles. No bespoke error UI.

Honest, engine-true warnings (e.g. “parquet stringifies floats”, “coercion may emit null”) surface at authoring time — guardrails before the run (principle 5).

4
DQ has two homes: a readable DQ Report here and the native Testing view — reusing flogo-3x's unit-test rig (bin-runner spawns the engine; results feed a TestController). Each DQ expectation = a pass/fail test; re-run like a suite.

07

Built on the flogo-3x baseline — reuse, don't rebuild

Data Pipeline ships as a feature inside the existing flogo3 extension, gated by a flag. It inherits the whole Flogo studio framework (custom-editor host, Angular canvas, mapper, diagnostics, runtimes, execution-history, unit-test rig) and adds only what's genuinely new: the /v1 engine client and the .datapipeline surfaces.
