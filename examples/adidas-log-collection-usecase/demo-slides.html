4Live — the stack-trace problem, solved

One exception, one record — never split

"log_level": "ERROR",
"message": "Unhandled fault in process instance 9916\njava.lang.NullPointerException: Cannot read field \"total\" ...\n\tat com.tibco.bw.Rest_Sample.OrderProcess.computeTotal(OrderProcess.java:77)\n\tat com.tibco.bw.core.runtime.ActivityFacade.execute(ActivityFacade.java:212)"

The podlog source stitches multiline Java stack traces into a single record before they ever reach S3 — the embedded newlines are just part of one field. Nothing downstream ever sees a split exception again.

This directly answers a pain point they likely have today with Fluentd's concat plugin — call that out by name if they've mentioned it.

Run it, then re-open the latest S3 object and show cluster/environment changed on the new record. This is the "you don't need a new build to promote this to prod" moment — sells itself to platform teams.
6Reliability — no silent data loss

At-least-once, with a dedupe key

Position registry + checkpoint

Crash-safe file, advanced every 5s. A pod restart resumes exactly where it left off — never re-reads the whole log, never silently skips ahead.

idempotency_key

Deterministic per-record key. Downstream consumers dedupe on it, so at-least-once delivery never becomes duplicate-counted metrics.

validate → DLQ

Malformed/null lines are routed to a node-local DLQ instead of dropped — reconcilable, never silently lost.

No live action needed — this is a talk-track slide. If asked "what happens if a pod dies mid-file?" this is your answer: checkpoint resumes, idempotency_key protects downstream counts.
