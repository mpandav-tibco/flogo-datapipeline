# Example 15 — Checkpoint & Resume

**Mode:** ETL (Extract, Transform, Load)
**Source:** CSV file — 5000 rows
**Transform:** Filter (`value > 50`)
**Sink:** Null (discard)
**Feature:** `checkpoint/file`, resume from token, `Skip()` logic

This example demonstrates how the Flogo Data Pipeline engine survives an
unexpected termination mid-run and resumes from exactly the last committed
row — zero row loss, zero row duplication.

---

## What You Will Learn

- How to configure `checkpoint.type = "file"` in a pipeline definition.
- What a checkpoint token looks like on disk and what each field means.

  are written.

- When to set `deleteOnSuccess: false` (debugging / auditing) vs. `true`
  (clean-run housekeeping).

## Concept: What Is a Checkpoint?

A **checkpoint** is a lightweight JSON token written by the engine to disk
after every batch of committed rows.  It records:

- How many rows have been successfully read from the source and committed to
  the sink (`rowsProcessed`).
- The wall-clock time the token was last written (`timestamp`).
- Enough source metadata to reopen and fast-forward the file on the next start
  (`source`, `sourcePath`).

If the process is killed between two checkpoint writes, at most
`intervalRows - 1` rows of progress are lost — the engine will re-process
them on resume.  Because checkpoints are written *after* sink commit, rows
are never silently skipped.

### Checkpoint file format

```json
{
  "pipeline":      "checkpoint-resume",
  "rowsProcessed": 2000,
  "timestamp":     "2026-07-08T14:23:01Z",
  "source":        "csv",
  "sourcePath":    "./data/big_file.csv"
}
```

| Field | Type | Meaning |
|-------|------|---------|
| `pipeline` | string | Matches the `"name"` field of the `.datapipeline` file — used to locate the correct token on restart |
| `rowsProcessed` | int | Number of source rows committed to the sink; engine calls `Skip(rowsProcessed)` at the next startup |
| `timestamp` | string | UTC ISO-8601 instant when this token was written — useful for auditing stale checkpoints |
| `source` | string | Source type tag (`"csv"`, `"jdbc"`, `"parquet"`, …) — selects the correct Skip() implementation |
| `sourcePath` | string | Path the source was reading from — sanity-checked on resume; mismatch causes a startup error |

## Concept: How Resume Works (`Skip()` Logic)

When the engine starts and finds a valid checkpoint token it:

1. Opens the source as usual (e.g., opens `big_file.csv`, reads the header).
2. Calls `source.Skip(rowsProcessed)` — reads and discards the first
   `rowsProcessed` data rows **without** passing them through transforms or
   the sink.  This is O(N) in sequential I/O but O(1) in memory; rows are
   consumed one at a time, never buffered.
3. Resumes normal batch processing from row `rowsProcessed + 1`.
4. Continues writing checkpoint tokens on the same `intervalRows` /
   `intervalSeconds` schedule.
5. On clean finish the final token is written (`rowsProcessed = total`), then
   the pipeline exits with code `0`.

```
First run (interrupted at row 2000):
  Row 1 ──► filter ──► null sink
  Row 2 ──► filter ──► null sink
  ...
  Row 1000 ──► [CHECKPOINT WRITTEN: rowsProcessed=1000]
  ...
  Row 2000 ──► [CHECKPOINT WRITTEN: rowsProcessed=2000]
  << SIGTERM received >>
  [flush in-progress batch]
  [final checkpoint written]
  exit(1)

Second run (resume from token):
  open big_file.csv
  Skip(2000) ──► rows 1-2000 discarded at source, never enter pipeline
  Row 2001 ──► filter ──► null sink
  Row 2002 ──► filter ──► null sink
  ...
  Row 3000 ──► [CHECKPOINT WRITTEN: rowsProcessed=3000]
  ...
  Row 5000 ──► [CHECKPOINT WRITTEN: rowsProcessed=5000]
  exit(0)
```

## Sample Data

`data/big_file.csv` is generated by `setup.sh` using a Python 3 script
(`data/generate_big_file.py`) with a fixed seed (`42`), so the file is
byte-for-byte identical on every machine.

**Schema:**

| Column | Type | Description |
|--------|------|-------------|
| `id` | int | Sequential row number, 1–5000 |
| `data` | string | Label of the form `"data_<id>"` |
| `value` | int | Pseudo-random integer in [1, 100] |

**Representative rows:**

```
id,data,value
1,data_1,15
2,data_2,72
3,data_3,6
4,data_4,87
5,data_5,51
...
5000,data_5000,43
```

**Distribution:**

| Condition | Count (approx.) | Effect |
|-----------|-----------------|--------|
| `value > 50` | ~2500 | Pass the filter — forwarded to sink |
| `value <= 50` | ~2500 | Dropped by filter transform |

The exact counts are printed by `setup.sh` after generation.

- `flogo-datapipeline` binary on your `PATH`.
- Python 3 on `PATH` (recommended for reproducible data generation; falls back
  to `$RANDOM` in bash if unavailable).
- Run all scripts from the `15-checkpoint-resume/` directory.

### Step 2 — Interrupt the pipeline mid-run

```bash
./interrupt.sh
```

This starts `flogo-datapipeline` in the background, waits 2 seconds, then
sends `SIGTERM`.  The engine flushes its in-progress batch, writes a final
checkpoint token to `./checkpoints/checkpoint-resume.json`, then exits.

```

========================================
--> Starting pipeline in background...
    (will send SIGTERM in 2 seconds)
    PID: 12345
--> Sleeping 2 second(s)...

    Process exited.
========================================

========================================

  ----------------------------------------

```

The exact `rowsProcessed` depends on machine speed. On a fast laptop the
engine may finish all 5000 rows before the 2-second kill fires — in that case
the token will show `rowsProcessed: 5000`, which is still a valid checkpoint
(resume will fast-forward the entire file and exit immediately).

## Verifying Zero Row Loss

The guarantee is structural: a checkpoint token records only rows that have
already been committed to the sink.  If the engine crashes before writing a
token, the worst case is that the rows processed since the last token are
re-processed on the next run (at-least-once delivery).

To verify manually:

1. After `interrupt.sh`, note `rowsProcessed = N` from the checkpoint file.
2. After `resume.sh`, note `rows_read` in the pipeline log — it should equal
   `5000 - N` (the rows that were remaining).
3. `N + rows_read` must equal `5000` — every source row was processed exactly
   once (or at most once in the at-least-once case near the crash boundary).

For this example, with a null sink, there is no persistent output to count.
In a real pipeline (e.g., sink to a JDBC table with `onConflict: upsert`),
you would query `SELECT COUNT(*) FROM target_table` and compare against the
expected row count after a successful resume.

## Checkpoint Configuration Reference

### `checkpoint` block

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `type` | string | Yes | — | `"file"` — write tokens to the local filesystem. `"none"` — disable checkpointing (pipeline always starts from scratch). |
| `path` | string | Yes (when type=file) | — | Directory where checkpoint JSON files are written. Created automatically if it does not exist. One file per pipeline (named `<pipeline-name>.json`). |
| `intervalRows` | int | No | `1000` | Write a checkpoint token after every N rows are committed to the sink. Lower values reduce potential row re-processing on crash at the cost of more I/O. |
| `intervalSeconds` | int | No | `30` | Write a checkpoint token if N seconds have elapsed since the last write, regardless of row count. Useful for pipelines that produce rows slowly (e.g., throttled API sources). |
| `deleteOnSuccess` | bool | No | `true` | When `true`, the checkpoint file is deleted after the pipeline exits with code 0 — keeps the checkpoints directory clean. When `false`, the final token is kept on disk, which is useful for debugging and auditing. Set to `false` in this example so you can inspect the file after a clean finish. |

### Choosing `intervalRows`

| Scenario | Recommended `intervalRows` |
|----------|---------------------------|
| Fast I/O sink (null, parquet, local JDBC) | 5000–10000 |
| Slow I/O sink (remote JDBC, object store) | 500–2000 |
| Idempotent sink with upsert semantics | 1000–5000 |
| Append-only sink (Kafka, log file) | 100–500 (minimise re-delivery window) |

### Interaction with `performance.batchSize`

`batchSize` controls how many rows are buffered in memory per internal batch
before being flushed to the sink.  A checkpoint is written after every
`ceil(intervalRows / batchSize)` flushes.  Setting `batchSize > intervalRows`
means checkpoints fire on every flush — the two controls are independent.

In this example: `batchSize=500`, `intervalRows=1000` → checkpoint after
every 2 flushes (every 1000 rows).

## When to Use Checkpointing

| Situation | Use checkpoint? |
|-----------|----------------|
| Long-running jobs (>1 min) on unreliable infrastructure | Yes — always |
| Kubernetes Jobs / ECS tasks that may be evicted | Yes |
| Nightly batch on stable bare-metal | Optional — reduces re-run time if failures are rare |
| Micro-batches (<1000 rows per run) | No — overhead outweighs benefit |
| Streaming pipelines (Kafka source) | Use the HWM transform instead (see example 12) |
| Sink is idempotent (upsert by PK) | Ideal — safe to re-process checkpoint boundary rows |
| Sink is append-only (Kafka, log) | Use carefully — rows near crash boundary may be duplicated |

## Troubleshooting

### Pipeline finishes before the kill signal fires

The dataset may be processed in under 2 seconds on fast hardware.  The
checkpoint file will show `rowsProcessed=5000` — the resume run will
fast-forward and exit immediately with `rows_read=0`.  This is correct
behaviour.  To force a mid-run interrupt:

- Increase `KILL_AFTER` in `interrupt.sh` (e.g., `KILL_AFTER=5`).
- Or reduce `batchSize` in the pipeline file (smaller batches → more time
  spent on I/O per row).
- Or increase the dataset size: edit `generate_big_file.py` and run
  `python3 data/generate_big_file.py 50000` for 50,000 rows.

### No checkpoint file after `interrupt.sh`

The pipeline was killed before it reached the first `intervalRows` boundary
(1000 rows).  The engine had no committed progress to save.  Increase
`KILL_AFTER` or decrease `intervalRows` in the pipeline file, then re-run
`interrupt.sh`.

### "checkpoint mismatch" error on resume

The `sourcePath` in the token does not match the current `source.path` in the
pipeline file, or the pipeline was renamed.  Either restore the original path,
or delete the stale checkpoint file and start from scratch (`./setup.sh`).

### Stale checkpoint from a previous example run

Run `./setup.sh` — it removes all `*.json` files from `./checkpoints/` before
generating fresh data, ensuring a clean slate.
